# E4 事前登録手続きの実装と試験運用（2026-10-26）

## 1. 実装したもの

- `run_prereg.py` と `e4/` で、事前登録の手続きを実装した。
  - 登録：仕様と依存ソースの md5 を凍結し、追記専用の登録記録に残す。
  - 実行前の検証：仕様の改変、ソースの変更、seed の重複があれば実行を拒否する。
  - 掃引と判定規則の変種：評価単位ごとに実行する。
  - 判定：登録した規則だけで判定する。
  - 整合性検査：規則に依存しないと登録した指標が、変種の間で一致するかを自動で照合する。
- 改ざん検出は試験で確認した。登録済み仕様の判定閾値を書き換えた複製は、「spec md5 not found in registry」で実行を拒否された。
- 使い方は `README.md` にある。

## 2. 試験運用の結果

評価用 seed 11〜60 は、登録前に一度も実行していない。調整用 seed から試運転したのは MinACS の seed 1 と v2 の seed 2 だけで、この事実は仕様に記録した。

### P1（MinACS、学習の有無）

**r1：整合性検査が実装の誤りを検出した。**

- 規則に依存しないはずの $T_{\mathrm{col}}$ が、判定規則の変種の間で 471 単位において異なった。
- 原因はアダプタにあった。背景列の長さを Recover の地平に依存させていたため、贈与の時刻が変種ごとに変わっていた。
- r1 の結果は記録どおり保存してある。修正したうえで新しい id（r2）として登録し直し、仕様に経緯を記載した。r1 の結果を見た後の登録であることも仕様に明記してある。

**r2 の結果（整合性検査は 0 件で一致）**

| 仮説 | 内容 | 判定 | 件数 |
|---|---|---|---|
| H1 | 学習あり（learn）の $T_{\mathrm{col}}$ ≥ 学習なし（no-learn） | 支持 | 900 単位中、≥ 880、> 267、< 20 |
| H2 | 崩壊直前の生存時刻に、Recover=1 となる外的作用が 3 種すべてではない（地平 5／10／20、規則 first／hold2 の 4 変種） | 4 変種すべて支持 | 1251 / 1251 |
| H3 | 崩壊前に必ず閉塞を経る（このモデルの記述） | 支持 | 1251 / 1251 |

**H2・H3 は、ほぼ失敗しえない仮説だった（登録の欠陥）。**

- H3 は、このモデルの構造から必ず成り立つ。全数で確認したところ、$s=1$ から崩壊しうる $(x,e)$ の組 92 個はすべて $A=\emptyset$（閉塞）だった。
- H2 についても、崩壊の直前の状態で 3 種の外的作用のすべてが即座に回復させる組は 0 個だった。地平内での継続まで含めた全数の分析はしていないが、構造上ほぼ確定していると読める。
- したがって、H2 で「判定が規則の変種に依存しない」と出たことは、規則への頑健性の証拠にはならない。
- この反省から、今後の登録では各仮説に「何が起きれば反するか、それがこのモデルで起こりうるか」（`how_it_could_fail`）の記載を必須にした。

**H1 について：**

- 学習ありの方が早く崩壊した単位が 20 件（2.2%）あった。
- 登録した規則では支持だが、「学習は常に有利」とは言えない。

### P2（v2 トイ、ドローンの有無）

| 仮説 | 内容 | 判定 | 件数 |
|---|---|---|---|
| H4 | ドローンあり（drone）での個体 i の $T_{\mathrm{col}}$ ≥ なし（no_drone） | 判定不能 | 450 単位中、≥ 376（83.6%）、> 306、< 74（16.4%） |
| H5 | 同じく個体 j について | 判定不能 | ≥ 395（87.8%）、> 274、< 55（12.2%） |

- 崩壊しなかった単位は、i でドローンあり 117 件・なし 75 件、j で 40 件・25 件だった。
- 救助者がいる方が崩壊の遅い単位が多い一方、早く崩壊した単位も 12〜16% あった。
  - 救助の配達が軌道そのものを変えるためと考えられるが、要因分析はしていない（未検証）。
- v2 の報告では、default（seed 1）の 1 例から「救助が閉塞を解いた」経過を示した。その例自体は正しいが、seed と数値を変えると、救助者の存在が崩壊を遅らせる方向に一様にはそろわない。これが事前登録の手続きで得た結果である。

## 3. 開示事項

- P2 の実行中に `e4/adapters.py` を編集した（P1 の修正のため）。
  - P2 は実行開始時に登録どおりのソースであることを検証してから走っており、編集したのは MinACS 用の関数だけである。
  - ただし、現時点で P2 の仕様を再検証すると「ソース変更」で拒否される。P2 を再現するには、登録時のソースを復元する必要がある。登録時の md5 は仕様に記録されている。
- P1 r2 の実行後、`e4/prereg.py` に `how_it_could_fail` の必須化を加えた。このため、現時点では P1 r2 も再検証で「ソース変更」となる。r2 の実行自体は、開始時に登録どおりであることを検証してから行った。今後は、この修正後のソースで新しい id として登録する。
- 「作り手と別の検証者」の項目は、私が作り手なので実施できていない。照合に必要なものは揃っている：
  - 仕様（specs/）
  - 登録記録（registry.log）
  - 単位ごとの全記録（results/*_units.jsonl）
- E4 は手続きの枠組みである。今回の P1・P2 は試験運用で、論文に寄与する主張を立てるためのものではない。
